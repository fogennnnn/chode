## Z6P Integration: What Was Built

### Architecture Overview

Z6P (Z6 Plan) is a **local-first state management protocol** for provider switching. Replaces remote HTTP-based HEMO vault with filesystem-based persistent memory.

**Design Principles:**
1. **Hash-bound integrity:** Every state change anchored to SHA-256 hash
2. **Local storage:** `.chode/memory/` directory, no external dependencies
3. **Z6 state vectors:** 6-element encoding (step, status, provider_health, capacity, queue_depth, error_state)
4. **Constraint validation:** Pre/post conditions on plan steps
5. **Handoff protocol:** Serialized state preserves context between provider switches

### Module 1: local-memory.js

**Purpose:** Filesystem-based persistent memory with integrity checking

**Key Components:**
```javascript
// Directory structure
.chode/memory/
├── sessions/      // Session state files
├── audit/         // Hash audit logs
└── handoffs/      // Provider handoff state

// Z6 state vector indices
Z6_STATE = {
  STEP: 0,           // Current step index (0-5)
  STATUS: 1,         // Session status (0=active, 1=paused, 2=completed, 3=failed, 4=blocked, 5=waiting)
  PROVIDER_HEALTH: 2, // Provider health score (0-5)
  CAPACITY: 3,       // Available capacity (0-5)
  QUEUE_DEPTH: 4,    // Queue depth (0-5)
  ERROR_STATE: 5     // Error state (0-5)
}
```

**Core Functions (as actually exported by `getMemoryManager()`):**
- `createSession(sessionId, metadata)` / `getOrCreateSession(sessionId)` - Session lifecycle; storage-loads **verify the stored hash and message hashes, throwing on tampering**
- `addMessage(sessionId, message)` - Append message with per-message `hash`/`selfHash`
- `setHandoff(sessionId, handoff)` / `getHandoff(sessionId)` - Handoff stored as its own object; `getHandoff` **verifies the hash and throws `Handoff corrupted: hash mismatch` on tampering**
- `updateStateVector(sessionId, updates)` / `getStateVector(sessionId)` - Z6 vector writes (modulo-6) and reads
- `setPlan(sessionId, plan)` / `getPlan(sessionId)` - Plan persistence
- `verifySession(sessionId)` - **Disk-based** integrity check (recomputes hashes from `meta.json` on disk, never from the in-memory copy — the in-memory variant was tautological and never tested; fixed 2026-11-02)
- `compressSession(sessionId)` - Compress after N messages (threshold: 20)
- `listSessions()`, `getSessionSummary(sessionId)`, `exportSession(sessionId)`, `deleteSession(sessionId)` - Listing, summary, export, deletion

Note: there are **no** `saveSession(sessionId, state)`-style free functions, no `rotateOldSessions()` TTL machinery, and no `handoffs/` subdirectory. Only `sessions/` and `audit/` exist.

**Integrity Mechanism:**
```javascript
// Every write includes self-hash
state.hash = crypto.createHash('sha256')
  .update(JSON.stringify(state.data))
  .digest('hex');
```

### Module 2: plan-z6.js

**Purpose:** Z6Plan state machine with constraint validation

**Key Classes:**

**Z6Status Enum:**
```javascript
Z6_STATUS = {
  PENDING: 0,
  IN_PROGRESS: 1,
  BLOCKED: 2,
  DONE: 3,
  SKIPPED: 4,
  FAILED: 5
}
```

**Z6Constraint (real API):**
```javascript
// Types (static map): 0 FILE_EXISTS, 1 FILE_NOT_EXISTS, 2 SYNTAX_VALID,
//                     3 TESTS_PASS, 4 DEPENDENCY_DONE, 5 CAPACITY_AVAILABLE
// new Z6Constraint(type, params) — params {path} for file checks, etc.
// check(context) — sets {satisfied, checkedAt}; context.root defaults to cwd
// Z6Constraint.AND(constraints) / OR(constraints) — composites
```

**Z6Plan (real API — verified against source):**
```javascript
class Z6Plan {
  // new Z6Plan(steps, options) — options.id becomes the plan id when given.
  // Steps accept Z6PlanStep instances, legacy {index,text,files,check} maps
  // (normalized by legacyToZ6Plan/parsePlanToZ6), or serialized state objects.
  // this.state = [0,0,0,0,0,0] is the Z6 state vector.
  
  progress()           // { done, total, pct }
  getCurrentStep()     // first step not in DONE/SKIPPED/FAILED
  advanceStep()        // validate current step, advance past it
  updateState(updates) // verify + apply modulo-6 updates to this.state
  setState(state)      // verified state assignment
  addStep(step, at?)   // insert step; index defaults to end
  startStep(index)     // PENDING -> IN_PROGRESS (validates advance-lock)
  completeStep(index, ok) // via Z6PlanStep.complete(ok) bookkeeping
  updateStatusFromPrereq(index) // derives BLOCKED when pruned observables
  getProgress()        // percentage done
  serialize()          // full state incl. per-step hashes
  static fromSerialized(data, sessionId) // verified state restore
}
```
Step statuses change only via `startStep`/`completeStep`/`updateStatusFromPrereq`; pre/post conditions validate through `Z6PlanStep.check()` (`satisfiesAll`), not a per-plan `validateConstraints()`.

**Z6 Arithmetic:**
```javascript
Z6 = {
  add: (a, b) => (a + b) % 6,
  mul: (a, b) => (a * b) % 6,
  wrap: (n) => ((n % 6) + 6) % 6,
  isValid: (n) => typeof n === 'number' && n >= 0 && n <= 5
}
```

### Module 3: z6-integration.js

**Purpose:** Handoff protocol for provider switching

**Key Functions:**

**legacyToZ6Plan(legacySteps, sessionId):**
- Converts chode's existing plan format to Z6Plan
- Maps `{index, text, files, check}` → Z6Plan steps
- Initializes all steps as PENDING

**parsePlanToZ6(planText, sessionId):**
- Parses markdown plan (e.g., "1. Do X\n2. Do Y")
- Extracts dependencies (e.g., "Step 3 depends on Step 1")
- Auto-generates constraints from file references

**serializeHandoff(z6Plan, context):**
```javascript
{
  handoffId: String(z6Plan.id),     // session-keyed plan id (added 2026-11-02)
  state: { plan: serialized, provider, providerHealth, capacityState, timestamp },
  hash: sha256(JSON.stringify(state)),
  selfHash: sha256(JSON.stringify(state) + hash)
}
```

**deserializeHandoff(handoff, sessionId):**
- Verifies `handoff.hash` against the recomputed state hash
- Returns `{ plan, context, valid }` — `valid: false` (with a `reason`) on tampering
- `saveHandoffToMemory(sessionId, handoff)` / `loadHandoffFromMemory(sessionId, handoffId)` persist through `localMemory.setHandoff`/`getHandoff` (both added 2026-11-02, after they were found calling nonexistent `localMemory.storeMessage`/`getSession` and failing silently)

**chode.js integration points (real behavior):**
```javascript
// init/resume (~line 3567): load handoff from memory when savedProgress has one,
// unwrap deserializeHandoff() {plan,valid} into z6Plan; else build legacyToZ6Plan(planSteps, sessionId)
// execOne (~line 3843): updatePlanFromActions(z6Plan, call, out) after each tool call
// saveProgress: serializeHandoff(z6Plan, sessionId) -> saveHandoffToMemory -> keeps z6HandoffId
```

### Integration into chode.js

**Main Loop Integration (real):**
```javascript
// Init / resume
const handoff = await loadHandoffFromMemory(sessionId, savedProgress.handoffId);
const unwrapped = deserializeHandoff(handoff, sessionId);
const z6Plan = unwrapped && unwrapped.valid ? unwrapped.plan
  : legacyToZ6Plan(planSteps, sessionId); // file refs map to FILE_EXISTS pre-conditions

// After each tool call
z6Integration.updatePlanFromActions(z6Plan, call, out); // records touched files as in-progress

// On checkpoint (saveProgress)
const handoff = serializeHandoff(z6Plan, sessionId);
if (saveHandoffToMemory(sessionId, handoff)) z6HandoffId = handoff.handoffId;
```
(Any integration failure is swallowed by the surrounding try/catch by design — Z6P is an enhancement, not a hard dependency.)

## Key Architecture Decisions

### Why Z6 State Vectors?

**Problem:** Provider switching loses context. Remote HEMO vault adds latency + single point of failure.

**Solution:** 6-element state vector encoding:
- Compact (fits in single JSON object)
- Extensible (add new indices without breaking changes)
- Hash-verifiable (entire vector hashed together)
- Local-first (no network dependency)

**Trade-off:** More complex than simple `{ currentStep: 3 }`, but enables constraint validation + tamper detection.

### Why Hash-Bound Integrity?

**Problem:** Silent corruption goes undetected until catastrophic failure.

**Solution:** Every write includes SHA-256 hash of data. Load verifies hash before use.

**Implementation (actual local-memory.js behavior):**
```javascript
// Writes: canonical payload = JSON.stringify({id, stateVector, plan, handoff}).
// hash = sha256(payload); selfHash = sha256(payload + hash). meta.json holds
// {id, createdAt, updatedAt, messages, plan, handoff, stateVector, metadata, hash, selfHash}.
// Loads: getOrCreateSession recomputes the hash FROM DISK and throws
// 'Session corrupted: hash mismatch' before any data is returned; each stored
// message file is verified the same way. verifySession() is disk-based too.
// Handoffs: a plain handoff gets memory-level hash/selfHash keys added; a Z6
// handoff (which already carries state-hash keys) is stored untouched and
// verified with its own scheme on read (setHandoff/getHandoff, local-memory.js).
```

**Trade-off:** Adds ~1ms per read/write, but detects corruption before it propagates.

### Why Constraint Validation?

**Problem:** AI agents lie about completion. Plan steps execute out of order.

**Solution:** Pre/post conditions on each step:
```javascript
{
  id: 3,
  description: 'Add button component',
  preConditions: [
    { type: 'requiresFiles', paths: ['src/Button.tsx'] },
    { type: 'blocksTools', tools: ['edit'], untilFilesExist: ['src/Button.tsx'] }
  ],
  postConditions: [
    { type: 'expectsOutput', pattern: /export default Button/ }
  ]
}
```

**Enforcement:** `Z6Plan.validateConstraints(stepId)` returns `{ valid: boolean, reason: string }`

**Trade-off:** More plan definition overhead, but catches invalid state transitions.

### Why Local-First Memory?

**Problem:** HEMO vault requires HTTP, adds latency, single point of failure.

**Solution:** `.chode/memory/` directory with:
- Session files (JSON + hash)
- Audit logs (append-only hash chain)
- Handoff state (provider-switch serialization)

**Benefits:**
- Zero network calls for memory ops
- Works offline
- User controls data location
- Easier debugging (files are readable)

**Trade-off:** No cross-machine sync (by design - each session is isolated).

## Critical Understanding for Implementation

### What Makes Chode Different

**Not just another AI wrapper:**
1. **Free mode first:** Designed for keyless providers, failover is core feature
2. **Z6P protocol:** Custom state management, not generic agent framework
3. **Terminal-native:** TUI is primary interface, not afterthought
4. **Security boundaries:** Workspace containment, not just "run anywhere"
5. **Evidence-based:** Browser verification, not just "trust the model"

### Common Pitfalls to Avoid

**DON'T:**
- Don't assume providers are reliable (they rate-limit, change APIs, go offline)
- Don't trust AI completion claims (verify with constraints)
- Don't store secrets in memory (redact immediately)
- Don't block main thread (async I/O for memory ops)
- Don't assume test environment matches production (mock external deps)

**DO:**
- Do verify hash integrity on every read
- Do enforce constraints before step execution
- Do redact secrets in error messages
- Do use bounded waits (no infinite loops)
- Do test negative cases (what should fail)

### Z6P-Specific Gotchas

1. **State vector indices are fixed** - Don't reorder `Z6_STATE` enum
2. **Hash verification is synchronous** - Blocking by design (integrity > perf)
3. **Handoff includes provider context** - Provider-specific state preserved
4. **Constraints are validated locally** - No remote validation dependency
5. **No TTL rotation exists** - Sessions persist until explicitly deleted; `deleteSession()` is the cleanup path
